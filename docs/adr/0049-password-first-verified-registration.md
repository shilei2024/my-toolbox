# ADR-0049：注册页填写密码，邮件确认后激活

2026-11-17，已批准实施；部分替代ADR-0048的邮箱页面设置密码交互。

## Why / Alternatives Considered

用户明确要求符合常见习惯：邮箱、密码和确认密码先在注册页填写，邮件只确认。沿用待验证申请避免未验证User与会话；替代方案为继续在邮件页面设密，已被用户否决。

## Architecture / Future Impact

新增可空的申请password_hash，使用统一Werkzeug算法，正式注册时复制摘要到User/密码身份后清除临时副本。无明文凭据落库。旧d9无摘要申请仍可在邮件页面设密，避免已经发出的链接中断；新申请使用register-confirm确认路径，无重复密码输入。重发不改变摘要，新密码提交使原token/旧任务失效。账号/业务ID、微信权限及欢迎邮件事务规则保持。

## Security

GET不激活，确认POST需CSRF/HTTPS同源，避免预取/扫描误激活。统一提示、冷却、限流和一次性token延续。常见预设密码流程允许他人为邮箱发起申请，邮件明确非本人不要确认；本次依据明确产品要求作取舍，不声称它具有旧邮箱内设密方案的同等预注册风险。已有正式账号绝不覆盖，确认时传入其他密码不能覆盖已保存摘要。

## Performance / Cost

密码哈希计算移到初始提交，确认时复用摘要；没有重复哈希，无新增基础设施/依赖/SMTP账号。e0迁移只新增一列，旧申请默认NULL，不重写业务归属。保持既有行锁/邮件队列，备份和全部public行摘要核对沿用。

## Rollback Plan

先恢复库PG16与HTTPS完整回归，再停止写者、最终备份、使用--password-first升级。产生新确认链接后不可回退旧路由/dispatcher；保留新增列，失败前进修复，禁止删申请/降级用户数据。指南见[注册更新](../auth-refactor/13-password-first-registration.md)。
