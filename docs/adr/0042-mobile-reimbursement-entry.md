# ADR-0042：移动报销工作台复用识别、确认与派车事实源

日期：2026-10-29；状态：候选实现，待评审和恢复库/真机验收。基础上传见ADR-0041。

## Why / 决策

用户已验收上传同步，但要求在手机完整录入。使用四个原生tab：首页选择周期与仪表盘，发票上传及核对，派车单新增编辑删除，我的管理绑定和登录。继续共用Flask、PostgreSQL、owner/工具授权、原件与目录，不新建后台或移动业务库。

共享recognize_original只返回OCR建议，不写财务；移动草稿缓存到已有领域审计，以owner/票据/原件摘要复用并由PG咨询锁抑制并发付费。确认带快照及明确确认，复用save_invoice与关联明细同步，保留手机未编辑的手工明细。网站旧OCR契约仍可用。派车只更新vehicle行，保留ID与来源元数据，复用全aux快照、里程链与_summary，拒绝破坏已分摊行。

## Alternatives Considered

只上传再跳网站仍无法完成主要录入；自动把OCR当真值有误报销风险；另建小程序后台/队列或OCR供应商增加运维和不同步；另建草稿表当前没有独立生命周期必要。选择模块内同步OCR及现有审计，不把报销专有流程提升为通用平台服务。

## Future Impact / Performance / Cost

无DB迁移、新依赖、云资源。顺序识别、成功缓存跨周期复用，保持既有供应商与用量规则，额外OCR可能按现有云额度收费；失败或缺字段可以人工录入。同步识别占用worker，客户端90秒超时，平台既有供应商超时不扩张；本轮不许宣称所有票种完整准确。审计JSON按owner/action/invoice/source过滤，目前不新增索引；未来体量显著增长再测量并设计索引/独立草稿生命周期。

## Security / Observability

Bearer及private授权原边界不变，锁后复查，快照拒绝旧写；金额和所有权在服务器校验。识别/确认/派车审计记录操作，不把原件或供应商异常打印给用户。原生请求/上传/原件打开检查会话仍一致，退出换账号清页面缓存。测试用合成供应商验证协议，实际OCR效果必须真机另验。

## Rollback Plan

可回到0.9.48应用与客户端，f5结构和已确认/派车数据不删、不downgrade；新API客户端与旧后端不兼容，先发布后端再更新体验版。回滚先停写并留最终备份，恢复旧代码后检查网站及mobile401；业务差错单独依据审计核对，不能用旧备份覆盖上线后的正常录入。严禁重跑一次性e4→f5发布/迁移脚本。
