# ADR-0036：旧版无时区字段采用 UTC 写入、按中国标准时间显示

## 状态

已接受，2026-09-01。

## Why

主站旧版 SQLAlchemy 模型使用 PostgreSQL `timestamp without time zone`。如果应用把带时区的 Python `datetime` 直接写入该字段，PostgreSQL 会先按连接会话时区转换再移除时区。在数据库会话为 `Asia/Shanghai` 时，UTC 时间会先增加 8 小时，页面随后再次按 UTC 转为中国标准时间，最终显示错误。

平台仍需要保持“UTC 是存储和比较口径，中国标准时间是展示口径”，同时不能为一个显示问题引入新服务或高风险全表数据修改。

## 决策

1. 旧版无时区字段写入前统一生成不带 `tzinfo` 的 UTC wall time，使驱动按 `timestamp` 直接绑定，不触发会话时区转换。
2. 中国时间转换使用 IANA `Asia/Shanghai`，管理日志明确标注 `UTC+8`，Python 进程日志使用相同时区并输出 `+0800` 偏移。
3. 已有日志不自动批量偏移。历史记录可能来自不同时区的应用连接，无法在没有发布证据的情况下安全推断；发布后以新生成日志作为验收基准。
4. 新业务域继续优先使用 `timestamptz`；该兼容策略只服务仍使用无时区字段的旧版模型。

## Alternatives Considered

- 页面直接增加或减去固定 8 小时：不能解决写入时已经偏移的问题，并会破坏正确记录。
- 批量把历史日志减去 8 小时：无法证明所有历史记录都来自同一种会话时区，存在破坏审计数据的风险。
- 立即把全部旧表改为 `timestamptz`：长期方向正确，但涉及大量表锁、迁移和回滚，本次日志校准不需要承担该风险。
- 强制 PostgreSQL 连接启动参数为 UTC：部分生产连接池会拒绝额外 startup parameter；规范化绑定值更简单，也不改变共享数据库会话行为。

## Future Impact

后续迁移旧业务表时，应逐表把无时区 UTC 列转换为 `timestamptz`，并用业务证据确认历史数据解释方式。所有新平台模块直接使用带时区字段。

## Performance and Cost

没有新增查询、存储或基础设施费用。UTC 规范化和 `ZoneInfo` 均为 Python 标准库操作，运行开销可忽略。

## Security

修复不会扩大日志读取权限，也不改变日志消息脱敏规则。避免自动重写历史审计记录，降低数据完整性风险。

## Rollback Plan

回滚应用提交并重启服务即可；本变更没有数据库结构或数据迁移。回滚后旧版无时区字段会恢复原写入方式，因此只能用于紧急恢复，不能视为时间问题已解决。
