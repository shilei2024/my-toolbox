# ADR-0035：报销助手复用共享客户主数据

## Why

报销助手原先只保存自由文本客户等级，招待/出差明细中的客户也是自由文本；客户项目跟进模块已经拥有组织隔离的客户主数据、简称和评级。继续维护两套客户目录会造成名称、简称和等级漂移，也会扩大后续 OCR、写作或搜索模块接入客户上下文时的维护成本。

本次变更通过 Golden Rule：会影响生产主站，因此使用可空外键和兼容迁移；客户目录可被未来模块复用；不新增服务、缓存或队列；部署只需要现有 Alembic 流程；边界符合模块化单体和 PostgreSQL 事实源架构。

## Decision

- `customers` 是客户全称、简称和客户等级的唯一主数据；客户等级固定为 `0-1/A/AA/AAA`。
- `reimbursement_invoices.customer_id` 使用可空外键关联 `customers.id`，删除客户时置空，不删除历史报销记录。
- 报销页面只向当前登录用户暴露其有效组织内的未删除客户，并显示 `short_name`；简称为空时回退全称。
- 关联客户后，报销页面、明细和汇总实时读取客户主数据等级；原 `customer_level` 只保留为未关联/历史记录的兼容字段。
- 招待与出差明细 JSON 保存 `customer_id`，输出时根据客户主数据刷新简称和等级；历史自由文本继续可读。
- 匿名报销仍可不关联客户并手工选择受控等级，不会获得组织客户目录。
- “项目等级”仍使用 A/B/C/D；它描述项目机会评估，不与客户等级合并。

## Alternatives Considered

1. 在报销模块复制客户表：查询简单，但形成第二事实源，否决。
2. 只保存客户简称文本：不需要迁移，但客户改名和等级变化无法同步，否决。
3. 新建独立 Customer Service：当前规模会增加部署、鉴权和运维成本，模块化单体内的共享表已经足够，暂不采用。

## Future Impact

未来 OCR、PDF、写作和搜索模块需要客户上下文时，应复用同一组织客户目录和权限边界。若出现跨组织客户集团或独立客户服务需求，再以稳定内部契约抽离；不得从报销表反向构建客户主数据。

## Performance

每个报销请求至多加载一次当前组织客户目录并在请求内复用，避免逐发票查询。`customer_id` 有独立索引。组织客户数量明显增长后，可增加分页/搜索端点，但当前不引入缓存。

## Cost

仅增加一个可空列、外键和索引，不新增基础设施、第三方依赖或持续运行成本。

## Security

服务端不信任浏览器提交的客户 ID或等级。关联前必须验证当前登录用户的有效组织成员身份、客户组织、有效状态和未删除状态；匿名用户不能读取客户目录。跨组织或无效 ID 返回通用业务错误，不泄露客户是否存在。

## Rollback Plan

迁移为向后兼容加列，上一版本会忽略该列，因此紧急回滚优先恢复上一稳定应用版本并保留列。不要在生产事故处理中直接 downgrade；若已确认没有新等级或客户关联数据，才可在备份后执行 downgrade。恢复数据库时使用发布前备份。
