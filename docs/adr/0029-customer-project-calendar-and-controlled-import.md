# ADR 0029: 共享工作日日历与受控 Excel 导入边界

## Status

Accepted — 2026-08-28。适用于客户项目 Phase 4 首发增强。

## Why

普通周一至周五无法表达中国法定假日和周末调休，会让提前、逾期和升级提醒日期偏移。历史项目又常存在 Excel 中，直接批量写库会把脏数据、重复记录和错误负责人带入生产，且难以定向恢复。

Golden Rule 结论：两项能力都会改变生产业务行为，因此继续受功能开关、统一后台、RBAC、审计和 staging 门禁保护；工作日日历属于可被未来任务/通知模块复用的共享能力，导入批次属于客户项目域；稀疏日期覆盖和数据库批次比引入第三方日历服务、ETL 服务或队列成本更低；固定模板、预览和发布手册方便初学者维护；方案保持 PostgreSQL 事实源和模块化单体边界。

## Decision

1. 共享层新增组织日期覆盖：未配置按周一至周五，显式记录可把任何日期设为工作日或休息日，不自动猜测中国法定调休。
2. 日历只影响“提前 N 个工作日”“逾期 N 个工作日”和停滞经理升级；跟进到期日仍尊重业务填写的具体日期。日历或策略变化取消未发送旧提醒并递增策略版本。
3. Excel 首发只接受固定 XLSX 模板，限制 5MB、1000 行、500 个 ZIP 成员、25MB 解压总量和异常压缩比。文件只在内存解析，不保存原始内容。
4. 预览阶段不创建业务对象，只保存文件摘要、识别映射、规范化负载和逐行错误。确认阶段只提交有效行并复用客户/项目领域服务。
5. 撤销通过软删除处理创建版本未变化的项目；项目被跟进、编辑或流转后必须保留并标记 `not_revertible`。批次和审计不删除。
6. 首发导入与日历仅提供同源服务端页面，不开放公共 API，不新增队列、对象存储或后台线程。

## Alternatives Considered

- 自动同步公共假日 API：依赖上游准确性和网络，且不同组织可能采用不同工作制，因此拒绝。
- 仅维护“假日”列表：无法表达周末调休工作日，因此拒绝。
- 上传后直接写库：反馈快但无法阻止脏数据，拒绝。
- 保存原始工作簿便于重跑：增加敏感数据留存和对象存储治理成本；首发以 SHA-256 与规范化行审计替代。
- 无条件整批撤销：会删除导入后产生的真实协作数据，拒绝。

## Future Impact

共享日历可供通用任务 SLA、账单周期和其他通知模块使用。导入未来可增加用户确认的字段映射、物料/竞品子表和异步大批次，但必须保留预览与条件撤销语义。附件和共享视图使用独立契约，不复用导入文件存储。

## Performance

提醒扫描只加载项目相关日期前后 45 天的覆盖。导入同步上限 1000 行并使用组织/规范名索引，禁止无界工作簿；超过该规模需评审异步任务。批次页面最多展示 1000 行、历史列表最多 50 个批次。

## Cost

新增四张小型 PostgreSQL 表和有限解析 CPU，不新增云服务、Redis、常驻 worker、假日订阅或对象存储费用。原始文件不落盘减少备份与合规成本。

## Security

日历由统一平台管理员维护；导入只允许组织管理员/业务经理。XLSX 在解析前执行大小、成员、解压预算、加密和压缩比检查。跨组织批次返回 404，错误不暴露内部栈；审计不保存原始文件或联系人电话。

## Rollback Plan

先停止提醒扫描并关闭客户项目功能开关，再回退应用。保留日历、批次、行记录、已创建业务对象和审计，不在事故中 downgrade。业务撤销使用批次条件撤销；不能撤销的项目走正常软删除/阶段流程。只有完成备份恢复演练和独立审批后才允许清理新增表。
