# ADR-0046：发票助手普通账号的个人客户空间

日期：2026-11-11。状态：实现完成，候选待发布验证。

## Why

发票助手按账号授权，新增客户却依赖独立的客户项目模块、试点名单及组织销售角色。普通已授权账号因此没有新增入口。放开按钮无法解决服务端权限与客户负责人校验。

## Decision

两端共用 `_customer_creation_enabled` 与 `_create_invoice_customer`。有效登录账号拥有发票助手授权（管理员沿用既有授权规则）即可新增客户。仍有原组织创建权限的账号继续走原路径，其余账号创建个人客户。

继续使用唯一 `customers` 表、相同字段校验与审计。个人客户的 `organization_id` 指向现有 organizations 中的独立数据容器，其稳定 UUID 由固定命名空间与用户主键生成。只在成功创建事务中按需创建，不创建任何 OrganizationMembership，不授予客户项目角色。命名空间是持久化契约，不能随版本或密钥改变。

现有 Organization.status 保留值 `personal` 专用于此类容器，是不可切换的类型标识，不作普通启停状态使用；停用用户沿用用户状态。CRM 初始化和统一后台所有默认组织查询显式排除它，提醒规划器原先只处理 active，因此不会向个人容器建策略或授予成员。测试覆盖“个人容器早于业务组织创建”的场景。未来若组织类型继续增加，再迁移为显式 kind 字段，需同时迁移这些保留值；当前无需 schema 变化。

个人记录须同时匹配容器、创建者和负责人。目录还包含当前组织内原先允许选择的本人/历史共享客户；加入组织后个人客户仍可见。历史展示继续允许解析当前组织客户，避免旧发票名称消失。前端不能传入 owner 或 organization；失败全部回滚。网站和手机创建均锁定同一 User 行，防止首次并发创建两个容器。

## Alternatives Considered

- 给普通用户自动加入管理员组织或发放销售角色：会扩大组织与客户项目访问权限，否决。
- 新建个人客户表：分裂主数据且增加发票外键/导出适配，否决。
- 把 customers.organization_id 改可空并引入新审计作用域：本次需要多表迁移，现有组织容器足以表达隔离，暂不采用。

## Future Impact / Performance / Cost

客户领域服务提供个人容器能力，未来模块按各自权限显式复用；它不等于客户项目授权。每位实际新增客户的账号增加一条容器记录，不增加常驻服务或依赖。GET 没有建组织副作用；查询使用既有组织索引与请求级缓存。普通账号不会自动获得客户资料管理页，界面只说明等级源于所选客户。

## Security

入口检查有效账号与发票工具 grant；创建后检查无新增 membership、原角色未变。跨账号选择、伪造组织/负责人、无效字段、撤权和禁用均有回归测试；组织客户仍按原角色创建。既有 CRM 的创建权限和负责人校验保持原规则。

## Rollback Plan

无 schema、配置或依赖变更。先部署后端，旧网站/小程序可直接读取新的能力标志；客户端体验优化随下一次小程序上传发布。回滚代码保留个人容器、客户、审计和发票，不降级数据库、不删除新记录。旧代码不识别个人目录，回滚期间暂停关联个人客户的编辑，优先前滚修复。生产部署按现行发布清单备份与验证，不复用固定旧 SHA 的一次性发布脚本。
