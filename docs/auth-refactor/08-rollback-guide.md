# 08 Phase 1 回退与恢复

本文保留早期阶段的回退边界。当前完整候选已包含 Phase 2–6，新凭据/无密码账号启用后不得采用下面的早期代码回退；以[当前发布故障与恢复](10-release-runbook.md#8-故障与恢复)为准。

## 推荐：代码回退，保留新增数据

本阶段旧 User 密码仍是权威，所有旧接口/token 格式不变。回退到 Phase 1 前兼容代码时可保留新增 nullable/default 列和新表；旧读者忽略它们。回退前确认未开启 Phase 2+ 的新凭据/新账号行为；不能把此结论扩展到后续可空邮箱、Argon2id 或全端撤销上线后。

不要把 downgrade 当作删除新密码副本/迁移审计的工具。`a6b7c8d9e0f1.downgrade()` 发现任一迁移运行/映射、新身份字段、验证状态或 epoch 使用时会拒绝，保护数据和撤销记录。

## 情况一：结构升级后尚未回填

仅在隔离环境且新增字段/表均未使用时，独立 Migration 支持 downgrade。自动化测试已验证升级→降级后旧表/原件/密码/权限不变。生产操作仍需审批、恢复演练与维护窗，本轮不执行。

## 情况二：回填中途失败

CLI 使用一个显式事务，任一 SQL/校验错误整体 rollback；run、影子身份、映射都不残留。查明聚合错误原因后重跑；不能 catch 异常后手工 commit。PG 等锁超过 5 秒同样回滚。SQLite 通过 BEGIN IMMEDIATE 抢占写锁。

## 情况三：回填成功后发现问题

停用新身份读取计划（本阶段本来未启用），保留新表供对账；继续旧登录。不要清空 users、不要回写旧密码、不要删除账号。修复回填/兼容代码，再在新的备份恢复副本演练。

## 情况四：隔离库恢复

从校验通过的备份恢复到新的隔离文件/数据库，比较旧 revision、源用户行、原件 BLOB、权限和旧 Token 摘要，再确认能重复演练。SQLite 文件备份恢复已经在临时测试中执行；真实 PG 恢复未执行，必须补验。

若以后确需生产完整恢复，应先停写、保全恢复点之后新增发票/订单/审计、评估损失并取得批准。恢复不能复活已撤销会话。禁止直接覆盖线上库作为常规代码回退方式。


## Phase 2 回退下限

b7c8d9e0f1a2 只在两张新表为空时允许 downgrade；任何会话或审计存在就拒绝删除。已签发新会话或发生撤销后，不能回退到忽略 auth_epoch 的旧 loader/移动认证，否则旧凭据可能复活。优先修复前进；必要时停止登录并保留所有表、epoch 和安全事件。恢复完整备份会丢失备份后的业务变更，必须单独评估，不能当作日常代码回退。保持 SECRET_KEY、用户ID和所有业务所有权不变；若发生凭据泄露，另走安全事件处置。
