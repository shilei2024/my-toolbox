# Phase 2：统一认证服务

## 范围与设计门禁（2026-11-14，用户已授权）

1. 影响生产认证入口：是，必须先完成迁移、PG16 隔离演练及预发布；本轮仅开发验证。
2. 可复用：账号、密码、身份、会话和安全事件属于所有工具共享的 auth 层。
3. 最低成本方案：复用 Flask/SQLAlchemy/PostgreSQL，不增加认证供应商、Redis 或独立服务。
4. 可维护部署：新增迁移，不移动用户或业务数据；提供配置、验证、回退边界。
5. 长期架构：users.id 保持 account_id，渠道只适配认证传输；授权继续由原业务模块负责。

## 实施计划

- 新增 account_service/session_service 及通用审计、WebSession 模型；新增 b7c8d9e0f1a2 迁移。
- Web 注册/登录、移动密码认证共用密码验证和状态判定；凭据以 users 为过渡权威，事务镜像 web_password 身份。
- 新 Web Cookie/Remember 使用不透明随机会话引用，数据库只保存摘要；旧数字 Cookie 仅在显式截止时间之前且 epoch=0 时接受。默认需要重新登录，账号及密码不变。
- 密码重置、停用、软删除统一锁定账号、递增 epoch、撤销 Web/移动会话和绑定挑战。管理员重置在持有用户锁后重新验证签名码，阻止并发重复兑换。
- 保持旧移动 Token 格式/响应；新增 epoch 校验。GET 退出展示确认，POST 才撤销。
- app.py、auth/routes.py、mobile_service.py、password_reset.py、admin/routes.py 接入；Gallery 使用真实 account_id。
- 注册竞争唯一冲突安全返回；密码/Token/邮箱不写安全审计。旧模型 setter 仅作为低层初始化辅助，生产变更经服务。
- 验证：注册/身份镜像、真实 Cookie/Remember、撤销后重放、两端重置、停用再启用、旧 Cookie 窗口、迁移回退、既有业务回归；PG 并发另列门禁。

估计为一个跨认证层开发里程碑。邮件发送和页面重构仍属 Phase 3；微信独立注册与立即授予 reimbursement 仍属 Phase 4；Generation 高风险操作的二次校验属 Phase 5。

## 回退与风险

新增会话生效后不能回退到忽略 epoch 的旧代码，否则被撤销 Cookie 可能复活。优先修复前进或停登录维护；保留数据库和新撤销校验，不能清空安全审计/epoch。本轮不执行生产发布。Phase 1 的真实数据对账、PG16 验收继续是发布门禁。


## 实施结果与边界

已新增共享账号/会话服务、通用审计模型、b7c8d9e0f1a2 迁移、隔离 upgrade-auth 命令和退出确认页。网站注册/登录、移动密码/微信会话签发、两端退出、管理员恢复码、停用/软删除已接入；绑定重认证使用同一密码检查。原私有工具中间件继续执行，不扩大既有授权。

旧数字 Cookie 兼容默认关闭，发布时可显式设置有时区的截止日期；这会要求旧会话重新登录，不改变账号或密码。新会话14天/1天固定到期，Cookie 签名及 CSRF 继续由现有组件提供。安全撤销不可通过功能开关关闭；启用以迁移+发布门禁控制，不能在启用后切回忽略 epoch 的旧实现。

密码镜像随合法凭据/状态变更更新；Phase 1 source_digest 保留原始基线不改写，后续合法变化不能靠重新跑 backfill 覆盖。完整数据迁移核对仍需恢复库。

本地测试结果见 07；未部署，未获得 PG16/真机/预发布结果。Phase 3 邮箱功能、Phase 4 微信自主注册和 Phase 5 下游高风险复查未被本阶段完成声明覆盖。
