# 客户项目跟进系统 PRD

> 适用行业：电子元器件代理商
> 文档状态：方案草案，可进入业务评审与技术拆分
> 版本：V1.0
> 日期：2026-08-27
> 主要读者：业务负责人、销售、PM、FAE、产品经理、架构师、开发、测试与运维
> 建议模块标识：`customer_projects`

## 1. 执行摘要

建设一个面向电子元器件代理商的客户项目协同模块，用统一、可追溯的数据替代个人 Excel、聊天记录和零散邮件。系统围绕“客户项目”聚合客户、项目阶段、推广物料、竞争方案、跟进记录、责任人、下一步动作和提醒，使销售、PM、FAE 与管理者在电脑和手机浏览器上看到同一份最新事实。

第一阶段建议作为 MindfulPenPal 主站中的独立业务域模块落地，复用现有 Flask 登录、用户、统一后台和 PostgreSQL，不新建独立 CRM 微服务，不把业务数据放入 AI generation service，也不依赖某一家邮件服务商。多端同步采用响应式 Web、服务端即时持久化、乐观并发控制与 15-30 秒轻量刷新；提醒采用 PostgreSQL 业务事实、通知发件箱和可替换调度器。该方案在满足生产可靠性的同时，部署单元少、成本低、便于初学者维护，并为未来其他工具复用组织、角色、通知、审计和任务能力保留边界。

量产、失败、暂停和归档是同一项目的生命周期状态，不进行跨表“搬运”。量产区、失败区和归档区均为筛选视图或统计投影，因此历史、关联物料、跟进记录和权限不会因状态变化而丢失。项目可重新激活，也可衍生为新项目并保留来源关系。

## 2. 背景与问题

电子元器件代理项目通常周期长、参与角色多、物料与竞品关系复杂。若信息分散在个人表格或聊天中，容易出现：

- 同一客户项目被多人重复登记，数据口径不一致；
- 项目阶段变化后没有同步给 PM、FAE 或管理者；
- 一个项目存在多品类、多料号、多竞争方案时，表格难以表达；
- 没有明确下一次跟进时间，或长期不更新而无人发现；
- 人员调整后历史和客户关系随个人流失；
- 量产或失败后项目被移走，无法恢复、复盘或衍生；
- 多人同时编辑时后保存的人覆盖先保存的人；
- 管理报表依赖人工汇总，无法解释数据来源。

## 3. 产品目标与非目标

### 3.1 产品目标

1. 建立客户项目的唯一业务事实源，完整表达客户、项目、物料、竞品、阶段、人员和跟进历史。
2. 让销售、PM、FAE 和管理者在不同终端安全协作，并及时发现他人更新和编辑冲突。
3. 在预设时间和长期未更新时自动提醒正确的人，形成“计划 - 跟进 - 更新 - 再计划”的闭环。
4. 支持项目量产、失败、暂停、归档、重新激活和衍生，保留完整历史。
5. 为管理者提供可信的项目漏斗、逾期、停滞、量产和失败汇总。
6. 复用平台认证、通知、审计、配置和任务能力，避免形成第二套后台。

### 3.2 成功指标

上线 3 个月后建议以以下指标验收业务效果，基线在试点前采集：

- 90% 以上在跟项目已录入负责人、当前阶段、下一步动作和下次跟进时间；
- 到期跟进在 2 个工作日内完成或明确延期的比例不低于 85%；
- 30 天未更新的活跃项目占比下降 50%；
- 量产与失败项目 100% 保留可查询的阶段和跟进历史；
- 同一项目重复记录率低于 2%；
- 邮件提醒任务无重复发送，发送状态可追溯率达到 100%。

### 3.3 非目标（V1 不做）

- 不替代 ERP、进销存、报价、订单、库存、财务或合同系统；
- 不提供原生 iOS/Android 客户端，先提供移动端自适应 Web；
- 不承诺 Google Docs 式逐字实时协同，先实现秒级保存、轻量刷新和冲突保护；
- 不在 V1 自动判断项目成功概率，评估等级由业务人员维护；
- 不在 V1 执行客户外呼、营销群发或自动联系客户；
- 不在 V1 存储供应商密钥、邮件账户密码或真实客户样例到代码仓库。

## 4. 关键设计原则与 Golden Rule 结论

### 4.1 五项设计门槛

1. **是否影响生产网站：是。** 新模块会增加路由、数据库表、权限入口和后台配置。必须使用功能开关、仅新增的向后兼容迁移、试点账号白名单、预览环境验证和可回滚发布。
2. **能否被未来模块复用：是。** 组织与成员、角色授权、通知发件箱、提醒策略、审计事件、标签和软删除应设计成共享能力；客户、项目、物料和竞争方案属于本业务域。
3. **是否存在更低成本方案：是，且已采用。** 复用现有 Flask 主站和 PostgreSQL；不新增常驻微服务、不要求 WebSocket、不在第一阶段引入 Redis。调度器只负责触发，数据库负责幂等和事实记录。
4. **初学者能否部署维护：能。** 默认只需一次数据库迁移、邮件配置和一个定时触发器；提供环境变量模板、验证命令、常见故障和回滚说明后即可运维。
5. **是否符合长期架构：是。** 保持统一管理后台、PostgreSQL 业务事实、可替换通知适配器、幂等高风险状态转换，不把 CRM 逻辑写入 AI generation service。

### 4.2 产品设计原则

- 先保存事实，再发送通知；邮件失败不能回滚项目更新。
- “删除”默认是可恢复的软删除；硬删除是受控的数据保留流程。
- 汇总区是视图，不是第二份数据；任何项目只有一个主记录。
- 竞争对手信息是可选的一对多关系，不以“没有竞品”阻止物料录入。
- 下一步动作和时间必须成对出现，避免只有日期没有行动内容。
- 关键字段变化必须可审计，不能只保留最新值。
- 所有时间以 UTC 存储，按组织时区显示；默认 `Asia/Shanghai`。

## 5. 用户、组织与权限

### 5.1 用户角色

| 角色 | 主要职责 | 默认数据范围 |
| --- | --- | --- |
| 平台管理员 | 账号、组织、系统级配置和故障处置 | 全平台，业务内容仅在授权和审计下访问 |
| 组织管理员 | 成员、角色、字段字典、提醒策略、数据恢复 | 本组织全部项目 |
| 业务经理 | 分配负责人、查看团队漏斗、审批关闭/重开 | 本部门或授权团队 |
| 业务负责人（Sales） | 创建项目、维护客户关系、跟进与预测 | 自己负责或参与的项目 |
| PM | 维护产品/品牌/料号、项目判断与资源协调 | 自己参与的项目 |
| FAE | 维护技术进展、样品/测试结论与风险 | 自己参与的项目 |
| 只读/审计 | 查询、筛选、导出允许的数据 | 被授权范围，只读 |

同一用户可以拥有多个角色；项目成员还需记录项目内职责（主业务、协同业务、PM、FAE、观察者）。V1 默认采用“组织角色 + 项目成员”两层授权，不引入复杂到字段级的权限系统。

### 5.2 权限矩阵

| 操作 | 组织管理员 | 业务经理 | 项目成员 | 只读 |
| --- | --- | --- | --- | --- |
| 新建客户/项目 | 是 | 是 | 是 | 否 |
| 编辑项目基础信息 | 是 | 是 | 是，限参与项目 | 否 |
| 分配/移除成员 | 是 | 是 | 主业务可建议或按策略允许 | 否 |
| 修改阶段 | 是 | 是 | 主业务；PM/FAE 可按配置允许 | 否 |
| 标记量产/失败 | 是 | 是 | 可发起；默认需业务经理确认 | 否 |
| 重新激活/衍生 | 是 | 是 | 主业务可发起 | 否 |
| 恢复软删除记录 | 是 | 是，限项目内容 | 否 | 否 |
| 查看审计日志 | 是 | 是，限数据范围 | 仅本项目可读事件 | 否 |
| 导出 | 是 | 是 | 按组织策略 | 按组织策略 |

所有服务端接口必须再次校验权限，隐藏按钮不是权限控制。

## 6. 核心领域模型

### 6.1 客户

必填字段：客户名称、所属组织、状态（有效/停用）、主负责人。建议字段：客户简称、统一客户编码、所属集团、行业、区域、客户等级、地址、备注、标签。联系人作为独立子记录，包含姓名、部门、职位、邮箱、电话、是否主联系人和备注。

同一组织内客户名称采用规范化后的重复提示，不做绝对阻断；管理员可合并重复客户，合并过程必须记录来源与审计事件。

### 6.2 项目

必填字段：客户、项目名称、当前阶段、主业务、下一步动作、下次跟进时间。建议字段：项目编号（系统生成）、终端应用、预计定点日期、预计量产日期、评估等级、成功概率区间、项目来源、年度潜在金额、币种、组织/部门、标签、保密等级、备注。

项目评估等级默认使用 A/B/C/D：A 为高价值且高确定性，B 为有明确机会，C 为早期或不确定，D 为低优先级/观察。客户等级是独立维度，统一使用 0-1/A/AA/AAA，并作为报销助手等模块共享的客户主数据；两者不得混用。成功概率应使用可配置区间而非伪精确小数；V1 默认 10%、30%、50%、70%、90%。

### 6.3 项目阶段状态机

默认阶段顺序：

`评估` -> `立项` -> `送样/验证` -> `小批` -> `试产` -> `定点` -> `量产`

辅助状态：`暂停`、`失败`、`归档`。组织管理员可以调整显示名称、排序和阶段 SLA，但系统保留稳定的内部代码，不能删除已被历史数据引用的阶段。

关键规则：

- 可跳过阶段，但必须填写原因；所有跳转写入阶段历史。
- 进入“量产”时，必须填写量产日期或预计日期确认、量产物料清单和结果说明。
- 进入“失败”时，必须选择失败原因，可补充竞争方、复盘说明和是否允许后续激活。
- 进入“暂停”时，必须填写暂停原因和可选恢复日期；到恢复日期可触发提醒。
- “归档”仅用于无需继续跟踪的记录，不等于物理删除。
- 从量产、失败、暂停或归档重新激活时，必须选择目标阶段并填写原因。

默认失败原因字典：客户取消、客户延期、技术不通过、价格原因、交期/产能、认证问题、竞争对手胜出、原厂策略、内部资源不足、信息重复、其他。

### 6.4 推广物料

一个项目可以包含任意数量的项目物料。每条物料包含：品类、推广品牌、推广型号/MPN、客户内部料号（可空）、应用位置、预计数量、数量周期（日/月/年/项目总量）、单位、目标价格（可选）、币种、样品数量（可选）、当前技术/商务状态、预计量产时间、主推标识、备注。

品牌、品类和单位来自可维护字典；型号保持文本以兼容未建档或新发布器件。后续如接入产品主数据，可增加可空的 `catalog_product_id`，但 V1 不强制建立完整料号主数据中心。

### 6.5 竞争方案

竞争方案必须关联到某一项目物料，而不是直接挂在项目上。每条包含：竞争品牌、竞争型号、竞争代理商/渠道、客户当前使用状态、报价信息（可选）、优势、劣势、信息可信度、信息来源日期和备注。

项目物料允许有 0 条竞争方案；这代表“暂未识别竞争对手”，不是脏数据。也允许同一物料存在多条竞争方案。若竞争型号未知，可只填品牌或代理商并标记“型号待确认”。

### 6.6 成员与职责

项目至少有一个主业务。PM、FAE 可为空，也可多人参与。成员记录包括用户、项目职责、是否主负责人、加入/退出时间和通知偏好。被停用账号不得继续接收提醒；其未完成项目需进入“待重新分配”列表。

### 6.7 跟进记录与下一步动作

每次有意义的跟进新增不可覆盖的活动记录，包含：跟进时间、跟进类型（电话/拜访/会议/邮件/样品/测试/报价/内部协同/其他）、摘要、详细内容、客户反馈、风险、决策、下一步动作、下次跟进时间、参与人员和创建人。

项目同时保存便于查询的 `last_meaningful_update_at`、`next_action`、`next_follow_up_at` 快照。新增跟进后在同一事务中更新快照。仅修改标签或错别字不算“有意义更新”，避免人为刷新停滞计时。

### 6.8 附件、标签与备注

V1 可预留附件元数据和对象存储接口，但若没有真实附件需求，不阻塞首发。启用时文件必须进入平台通用存储服务，数据库只保存对象键、文件名、大小、内容类型、上传人和校验值，不保存临时 URL。标签在组织内管理，可用于客户和项目筛选。

## 7. 功能需求

### 7.1 工作台与列表

登录后默认展示“我的工作台”：今日到期、已逾期、即将到期、长期未更新、待重新分配、最近更新。列表支持按客户、项目、阶段、评估等级、业务、PM、FAE、品牌、品类、型号、标签、更新时间和跟进时间筛选。

用户可以保存个人筛选视图。组织管理员可以发布组织共享视图。搜索需覆盖客户名称、项目名称、项目编号、推广型号和竞争型号。

### 7.2 项目详情

详情页按以下区域组织：

1. 项目概览：客户、阶段、评估、概率、关键日期、负责人、下一步动作；
2. 推广物料：多行物料及其技术/商务状态；
3. 竞争方案：按推广物料分组显示，可为空；
4. 跟进时间线：按时间倒序展示活动和阶段变化；
5. 成员与通知：业务、PM、FAE、观察者及各自通知设置；
6. 风险与待办：逾期动作、缺失字段、待确认信息；
7. 审计：对有权限的用户显示关键变化。

### 7.3 增删改查

客户、联系人、项目、项目物料、竞争方案、成员、标签、跟进记录和可配置字典均支持在权限范围内新增、查询、修改和删除。

“删除”采用软删除并记录操作者、时间和原因。普通用户删除后进入回收站，默认保留 30 天；组织管理员可恢复。涉及审计、阶段历史和已发送通知的记录不直接硬删，只能脱敏或按数据保留策略清理。

### 7.4 多端同步与并发编辑

- 所有写操作成功后立即写入 PostgreSQL，任何终端刷新后看到相同状态；
- 页面在前台时每 15-30 秒检查版本变化，列表和详情显示“有新更新”；
- 每个可编辑聚合维护 `version`。更新请求携带读取时的版本；版本不一致返回冲突，不覆盖他人内容；
- 冲突界面展示“你的内容”和“服务器最新内容”，允许刷新、复制后重填或由用户确认合并；
- 关键保存完成后显示保存时间和操作者；网络中断时不得显示已保存；
- 移动端至少支持项目查询、添加跟进、调整下一步动作和查看提醒。

V2 如验证出强实时需求，可在不改变业务 API 的前提下增加 SSE/WebSocket 事件推送；V1 不把长连接作为上线前提。

### 7.5 跟进提醒

创建或更新下一次跟进时间后，系统按组织策略生成提醒。默认策略：到期前 1 个工作日 09:00 提醒一次，到期当天 09:00 提醒一次；若到期后仍未完成，则次日 09:00 提醒一次并标记逾期。具体时间、工作日规则和收件角色可配置。

默认收件人是主业务，抄送项目内 PM/FAE 由组织或项目设置决定。提醒邮件包含项目编号、客户、项目、阶段、当前物料摘要、下一步动作、到期时间、最近一次有效更新和直达链接，不包含不必要的敏感字段。

当用户完成本次跟进、变更下次跟进时间、项目进入终态或暂停时，尚未发送的旧提醒自动取消。发送需使用唯一幂等键，例如 `项目 + 提醒类型 + 计划时间 + 策略版本`，防止调度重试造成重复邮件。

### 7.6 长期未更新提醒

每个活跃阶段配置停滞阈值。建议默认：评估 14 天、立项 14 天、送样/验证 10 天、小批 14 天、试产 14 天、定点 30 天；量产、失败、归档不触发停滞提醒，暂停按恢复日期处理。

达到阈值后先提醒主业务；再过 3 个工作日仍无有效更新，升级抄送业务经理；再过 7 个工作日可进入管理者“严重停滞”列表。相同停滞周期内按等级最多发送一次，新增有效跟进后重置周期。

### 7.7 邮件发送与通知中心

通知由通用通知服务处理，业务模块只提交通知意图，不直接调用 SMTP。V1 支持 SMTP 适配器，保留未来企业微信、钉钉、短信和站内通知适配器。

每封通知记录 `pending/sending/sent/failed/cancelled`、尝试次数、下次重试时间、供应商消息标识和脱敏错误码。默认最多重试 3 次并指数退避；永久失败进入管理后台告警列表。模板需要预览、测试发送和版本控制。

### 7.8 量产、失败、归档、激活与衍生

- **量产汇总区：** 查询状态为量产的项目，按客户、业务、品牌、品类、月份和年度统计，可回到完整项目详情。
- **失败汇总区：** 查询失败项目，按失败原因、竞争品牌、代理商、阶段和负责人复盘。
- **归档区：** 保存停止日常跟进但仍需查阅的项目。
- **重新激活：** 在原项目上新增状态变化事件，选择新阶段、新负责人、下一步动作和跟进时间，不删除旧历史。
- **衍生项目：** 创建新的项目编号和独立生命周期，记录 `derived_from_project_id`，由用户选择复制客户、成员、物料、竞争方案和标签；跟进记录默认不复制，只保留来源链接。

### 7.9 汇总与报表

V1 提供：项目漏斗、阶段停留时长、按负责人分布、逾期跟进、长期未更新、预计定点/量产时间分布、量产项目、失败原因、推广品牌/品类/型号覆盖、竞争品牌和竞争代理商统计。

报表必须说明筛选时间、数据范围、口径和生成时间。漏斗按项目当前阶段统计；历史转化率按阶段事件计算，二者不可混用。金额字段缺失的项目仍计入数量型报表。

### 7.10 导入与导出

考虑行业用户常有历史 Excel，建议 V1.1 提供模板化导入：先上传、预览字段映射和错误，再确认写入；同一批次必须可追踪和撤销未被后续修改的新增记录。导出受权限控制并记录审计日志，可导出当前筛选结果和项目详情，不默认导出联系人电话等敏感信息。

## 8. 业务规则与校验

### 8.1 必填与条件必填

- 新项目：客户、项目名称、阶段、主业务、下一步动作、下次跟进时间；
- 项目物料：推广品牌、推广型号或“型号待确认”至少一项，品类、预计数量和单位可先留空但进入“信息待补齐”；
- 量产：至少一条有效物料、量产日期/预计日期、量产说明；
- 失败：失败原因、失败说明；竞争对手未知时允许选择“未识别”；
- 暂停：暂停原因；建议填写恢复日期；
- 重新激活：目标阶段、原因、下一步动作、下次跟进时间；
- 衍生：新项目名称、目标阶段、来源项目和复制范围。

### 8.2 重复检测

新建项目时，对“组织 + 客户 + 规范化项目名 + 未关闭状态”做相似提示；对“同一项目 + 推广品牌 + 规范化型号”提示重复物料。提示允许有权限用户继续，不采用无法解释的硬阻断。

### 8.3 时间与工作日

数据库使用 UTC。界面与邮件按组织时区展示。工作日默认周一至周五，不自动推断中国法定调休；V1 可配置组织级节假日日历，未配置时明确按普通周历计算。

### 8.4 数据保留

审计事件、阶段历史和通知记录建议至少保留 3 年，具体周期由组织政策和法规要求确定。回收站默认 30 天。项目关闭不会触发自动删除。任何批量清理必须先生成影响清单并由管理员确认。

## 9. 页面与交互设计

### 9.1 信息架构

建议导航：`我的工作台`、`客户`、`项目`、`量产汇总`、`失败复盘`、`报表`；组织管理员额外看到 `成员与权限`、`字段字典`、`提醒策略`、`通知日志`、`回收站`。系统级设置仍位于现有统一后台，不创建独立管理员站点。

### 9.2 关键交互

- 快速新增项目使用分步表单：客户与项目 -> 成员 -> 物料 -> 下一步；允许保存草稿；
- 详情页顶部始终显示阶段、主业务、下一次跟进、是否逾期和最后更新时间；
- “新增跟进”是移动端首要操作，提交后可同时设定下一步；
- 量产/失败使用确认向导，展示将产生的业务影响，但不移动或复制数据；
- 空竞争方案显示“暂未识别竞争方案”，并提供新增入口；
- 缺失非必填信息以“待补齐”提示，不阻塞早期项目建立；
- 批量操作仅支持分配负责人、加标签、设置提醒策略等低风险动作；批量关闭需二次确认和逐项校验。

### 9.3 可用性与无障碍

支持桌面、平板和手机浏览器；关键状态不能只靠颜色表达；表单错误与字段相邻；键盘可完成主要操作；页面标题和表格结构清晰；中国用户界面优先使用简体中文，型号、品牌和行业缩写保留原文。

## 10. 推荐技术架构

### 10.1 选型结论

**V1 推荐：现有 Flask 主站内的模块化单体 + PostgreSQL + 独立可触发的通知处理命令。**

建议新增边界：

```text
浏览器（桌面/移动端）
        |
        v
现有 Flask 主站
  |- 认证与会话（复用）
  |- customer_projects 蓝图（页面/BFF）
  |- customer_projects 领域服务（规则/权限/状态机）
  |- shared notifications（通知意图/模板/发件箱）
  |- unified admin（组织、字典、提醒、失败通知）
        |
        v
PostgreSQL（唯一业务事实源）
        ^
        |
外部调度器 -> 受保护的命令或内部端点 -> 提醒扫描/发件箱发送
        |
        v
邮件适配器（SMTP 首发，可替换）
```

调度器可以是 Vercel Cron、腾讯云上的 systemd timer/cron 或未来 BullMQ；它只负责定时触发，不保存业务状态。无论触发器重复或中断，PostgreSQL 中的唯一约束、事务锁和幂等键都确保不会重复创建或发送同一提醒。

### 10.2 为什么不选择其他方案

- **不新建 CRM 微服务：** V1 业务量与团队规模尚不需要独立扩缩容；新服务会增加认证、部署、监控和网络故障面。未来当写入量、组织隔离或团队边界明确时再按稳定领域接口拆分。
- **不放入 generation service：** 客户项目不是 AI 生成任务，放入会破坏领域边界并扩大生产风险。
- **不把 APScheduler 放在 Web 进程：** Vercel/多 worker 环境可能不运行后台线程或重复执行。应由外部调度器触发幂等任务。
- **V1 不要求 Redis：** 项目协作和提醒可用 PostgreSQL 行锁、跳过锁定和发件箱可靠完成。达到吞吐阈值后再引入队列。
- **V1 不要求 WebSocket：** 轻量刷新加乐观锁已经满足跨终端一致性，部署更简单。强实时是可插拔增强项。

### 10.3 建议代码边界

```text
customer_projects/
  __init__.py            # Blueprint 注册
  routes.py              # HTML/BFF 路由，薄控制器
  api.py                 # JSON API
  forms.py               # 输入校验
  permissions.py         # 组织与项目授权
  services/              # 项目、跟进、状态机、衍生逻辑
  repositories/          # 持久化接口与 SQLAlchemy 实现
  notifications/         # 业务通知意图和模板参数
  queries/               # 列表、漏斗、停滞等读模型
  models.py               # 仅该领域模型
templates/customer_projects/
static/customer_projects/
tests/customer_projects/
```

共享的组织、通知和审计模型应放入清晰的共享模块；不得继续把所有新模型堆入根目录 `models.py`。实施前需创建 ADR，确认模块目录、迁移框架和调度器入口。

### 10.4 事务与一致性

创建跟进记录、更新项目快照、递增版本号和写入审计事件必须在同一数据库事务中完成。业务事务只创建通知意图/发件箱记录，不同步等待邮件供应商。发件箱发送器使用短事务领取任务，发送后记录结果；网络调用期间不持有长数据库锁。

阶段变更、量产、失败、重新激活、衍生、成员移除和批量导入均需幂等请求键。客户端超时重试不能产生重复阶段事件或衍生项目。

## 11. 数据设计

### 11.1 核心表

所有业务表包含 UUID/稳定主键、`organization_id`、`created_at`、`updated_at`、创建/更新人；可编辑聚合包含 `version`；可删除数据包含 `deleted_at`、`deleted_by` 和 `delete_reason`。

| 表 | 作用 | 关键关系/约束 |
| --- | --- | --- |
| `organizations` | 组织边界与时区 | 名称、状态、默认时区 |
| `organization_memberships` | 用户在组织中的角色 | 组织 + 用户唯一，可停用 |
| `customers` | 客户主数据 | 组织内规范化名称索引 |
| `customer_contacts` | 客户联系人 | 属于客户，可标主联系人 |
| `customer_projects` | 项目聚合根 | 客户、阶段、主业务、版本、来源项目 |
| `project_members` | 项目参与人和职责 | 项目 + 用户 + 职责唯一 |
| `project_materials` | 推广物料 | 属于项目，允许多品类/多型号 |
| `material_competitors` | 某物料的竞争方案 | 属于项目物料，数量可为 0..N |
| `project_activities` | 不可覆盖的跟进记录 | 有效更新标识、发生时间、创建人 |
| `project_stage_events` | 阶段历史 | 前后阶段、原因、操作者、发生时间 |
| `project_reminder_policies` | 组织/项目提醒规则 | 适用范围、版本、是否启用 |
| `notification_outbox` | 待发送通知事实 | 幂等键唯一、状态、重试字段 |
| `notification_deliveries` | 每个收件人的发送结果 | 发件箱 + 收件人唯一 |
| `audit_events` | 关键操作审计 | 对象类型/ID、动作、脱敏差异 |
| `project_tags` / `tag_links` | 组织标签和关联 | 组织内标签名唯一 |
| `project_status_catalog` | 可配置显示阶段 | 稳定代码不可改，可调整显示和 SLA |

### 11.2 关键字段建议

`customer_projects`：`id`、`organization_id`、`project_code`、`customer_id`、`name`、`normalized_name`、`stage_code`、`assessment_grade`、`probability_band`、`primary_sales_user_id`、`next_action`、`next_follow_up_at`、`last_meaningful_update_at`、`expected_design_win_at`、`expected_mass_production_at`、`actual_mass_production_at`、`close_reason_code`、`closed_at`、`derived_from_project_id`、`version`。

`project_materials`：`id`、`project_id`、`category_code`、`promoted_brand`、`promoted_mpn`、`customer_part_number`、`application_position`、`estimated_quantity`、`quantity_period`、`unit_code`、`target_price`、`currency`、`technical_status`、`commercial_status`、`is_primary`、`version`。

`material_competitors`：`id`、`project_material_id`、`brand`、`mpn`、`distributor`、`incumbent_status`、`strengths`、`weaknesses`、`confidence_level`、`observed_at`、`version`。所有字段均允许根据业务阶段适度为空，但至少需要品牌、型号、代理商之一或明确的“待确认”标记。

### 11.3 索引与查询

重点索引：组织 + 阶段、组织 + 主业务 + 下一跟进时间、组织 + 最近有效更新时间、客户 + 项目规范名、推广品牌/规范化型号、竞争品牌/规范化型号、未删除记录的部分索引、待发送通知的状态 + 计划时间。所有列表查询先限定 `organization_id`，再应用用户数据范围。

### 11.4 迁移策略

生产使用 PostgreSQL；SQLite 仅允许本地开发和单元测试。新增表先部署、再启用功能开关；字段从可空到必填必须经过“新增可空字段 -> 回填 -> 校验 -> 收紧约束”的兼容流程。迁移不得依赖 Web 进程启动时的 `create_all`。实施时需引入或统一正式迁移工具，并提供备份、预演和恢复步骤。

## 12. API 契约建议

内部页面可以使用服务端渲染，但核心写操作应有稳定 JSON 契约，便于移动端、未来前端和自动化复用。建议前缀 `/api/v1/customer-projects`。

| 方法与路径 | 用途 | 关键要求 |
| --- | --- | --- |
| `GET /projects` | 分页筛选项目 | 游标分页、组织与权限过滤 |
| `POST /projects` | 创建项目 | `Idempotency-Key`，重复提示 |
| `GET /projects/{id}` | 获取详情 | 返回 `version` 与权限能力 |
| `PATCH /projects/{id}` | 更新项目 | `If-Match`/版本，冲突返回 409 |
| `POST /projects/{id}/stage-transitions` | 修改阶段 | 校验状态机、条件必填、幂等 |
| `POST /projects/{id}/activities` | 新增跟进 | 同事务更新下一步与有效更新时间 |
| `POST /projects/{id}/reactivate` | 重新激活 | 目标阶段、原因、幂等 |
| `POST /projects/{id}/derive` | 衍生项目 | 复制范围、来源关系、幂等 |
| `POST /projects/{id}/materials` | 添加物料 | 支持暂无竞品 |
| `POST /materials/{id}/competitors` | 添加竞争方案 | 0..N 条，不设伪必填 |
| `DELETE /.../{id}` | 软删除 | 原因、权限、审计 |
| `POST /trash/{type}/{id}/restore` | 恢复 | 管理员/经理权限 |
| `GET /reports/...` | 汇总查询 | 明确口径、数据范围和时间 |

统一错误结构包含可公开的错误码、中文提示、字段错误和请求追踪 ID，不返回堆栈、SQL、内部路径或供应商原始错误。所有批量接口需限制条数和总负载。

## 13. 提醒处理时序

1. 调度器按固定频率触发“扫描到期提醒”命令或受签名保护的内部端点。
2. 扫描器读取到期且处于活跃状态的项目，计算策略版本和收件人。
3. 在事务内按幂等键插入发件箱；重复记录因唯一约束被忽略。
4. 发送器领取少量 `pending` 记录并标记 `sending`。
5. 通知适配器发送邮件，成功写 `sent` 和供应商标识；失败写脱敏错误、重试次数和下次重试时间。
6. 管理后台展示失败项和重试入口；重试仍沿用原幂等身份。
7. 监控检查扫描器心跳、积压量、最老待发送时间和失败率。

内部触发必须使用独立密钥签名、时间戳和重放窗口；不接受浏览器会话作为机器调用鉴权。密钥只保存在环境变量/密钥管理中。

## 14. 非功能需求

### 14.1 性能与容量

V1 设计基线：单组织 100 名活跃用户、10 万项目、每项目平均 10 条物料和 100 条活动；普通列表 P95 小于 2 秒，详情 P95 小于 2 秒，写操作 P95 小于 1.5 秒（不含邮件发送）。搜索与报表必须分页或限制时间范围，禁止无界导出。

### 14.2 可用性与可靠性

- Web 更新提交后必须得到明确成功/失败反馈；
- 邮件不可用时项目数据仍可正常写入；
- 定时器暂停后恢复执行不能漏掉未过保留窗口的提醒，也不能重复发送；
- 数据库备份与恢复流程必须覆盖本模块；
- 关键写入具备事务、幂等和审计。

### 14.3 安全与隐私

- 组织级数据隔离和服务端 RBAC；
- CSRF 防护、输入长度限制、输出转义、限流和安全会话沿用平台能力；
- 邮件中使用最小必要信息，项目链接需登录后访问；
- 敏感导出记录操作者、时间、筛选范围和文件摘要；
- 审计差异屏蔽联系人电话、邮箱等敏感值，必要时只记录“已变更”；
- 禁止把客户、竞争情报、真实邮箱和业务金额写入测试夹具或日志；
- 管理员代查业务数据需最小权限并留痕。

### 14.4 可观测性

指标至少包含：API 请求量/错误率/延迟、409 冲突数、提醒扫描心跳、待发数量、最老待发时长、发送成功率、永久失败数、逾期项目数和严重停滞项目数。日志使用请求 ID、组织 ID（不可逆或内部 ID）、对象 ID和错误码，不记录邮件正文和完整联系人信息。

### 14.5 兼容性

支持当前主流桌面与移动浏览器最近两个大版本；中文、英文品牌/型号和常见符号可正确输入、搜索和导出。型号规范化仅用于匹配，不改变用户原始展示值。

## 15. 配置项

建议环境变量只包含基础设施和密钥：邮件适配器类型、SMTP 主机/端口/加密模式、发件地址、凭据、内部调度密钥、功能开关。业务策略（阶段、SLA、收件角色、工作日、升级规则、回收站保留天数）存入 PostgreSQL 并由统一后台维护。

生产环境不得依赖默认密码或开发 SMTP。邮件发件域名应完成 SPF、DKIM 和 DMARC 配置；具体操作写入部署文档，不在日志打印验证记录中的密钥。

## 16. 测试与验收标准

### 16.1 核心验收场景

1. 用户能创建包含 3 种品类、5 条推广物料的项目，其中 2 条无任何竞品；保存、刷新和另一终端查看结果一致。
2. 同一项目物料能添加多条竞争方案，包含仅品牌已知、型号待确认的记录。
3. Sales 与 PM 同时编辑同一项目时，后提交者收到冲突提示，系统不静默覆盖先提交内容。
4. 到期前、到期日和逾期提醒按策略生成；同一任务重复触发 10 次仍只发送一份同键提醒。
5. 新增有效跟进后，长期未更新计时重置；只改标签不会重置。
6. 用户停用后不再收到邮件，其负责项目出现在待重新分配列表。
7. 项目进入量产后出现在量产汇总且原详情、物料、竞品和历史不变。
8. 项目失败后记录失败原因并进入失败汇总；可重新激活到指定阶段。
9. 从原项目衍生新项目时生成新编号，来源关系可见，按选择复制物料而不复制跟进历史。
10. 软删除项目后普通列表不可见、回收站可见，管理员恢复后关联数据完整。
11. 未授权用户通过手工构造 URL/API 仍无法读取或修改其他组织项目。
12. 邮件服务故障时项目更新成功，通知进入重试并在后台可见，不泄露供应商原始错误。

### 16.2 自动化验证

- 单元测试：状态机、必填规则、停滞计算、工作日、收件人、幂等键、权限决策；
- API/服务测试：CRUD、分页筛选、409 冲突、软删除/恢复、重新激活/衍生；
- PostgreSQL 集成测试：约束、索引、事务、并发领取、重复调度；
- 安全测试：跨组织访问、CSRF、越权、批量接口限制、日志脱敏；
- 端到端测试：创建项目 -> 添加物料/竞品 -> 跟进 -> 提醒 -> 量产/失败 -> 激活/衍生；
- 回归测试：现有登录、首页工具、统一后台、AI Gallery 入口及原有工具不受影响；
- 部署演练：预览/预生产迁移、功能开关启停、备份恢复和应用回滚。

### 16.3 Definition of Done

只有在代码、迁移、API、权限、自动化测试、预生产验证、安全/性能检查、监控告警、文档、备份恢复和回滚方案相互一致后，才可宣布完成。邮件“能收到”不能替代幂等、失败重试和审计验收。

## 17. 分阶段交付计划

### Phase 0：业务确认与架构冻结（约 3-5 人日）

确认角色、阶段字典、停滞阈值、量产/失败审批规则、组织边界、邮件渠道和历史数据规模；创建 ADR、数据字典、低保真原型和迁移策略。无生产变更。

### Phase 1：核心项目台账（约 15-20 人日）

组织/成员最小能力、客户、项目、阶段状态机、成员、物料、竞品、跟进记录、搜索筛选、软删除、审计、响应式页面和乐观锁。使用功能开关，仅试点用户可见。

### Phase 2：提醒闭环（约 8-12 人日）

提醒策略、到期/停滞计算、通知发件箱、SMTP 适配器、外部调度入口、重试、通知日志、心跳和告警。

### Phase 3：汇总与生命周期（约 6-10 人日）

量产/失败/归档视图、审批、重新激活、项目衍生、漏斗、逾期和失败复盘报表。

### Phase 4：迁移与增强（约 8-15 人日）

Excel 导入预览与撤销、受控导出、共享视图、节假日日历、附件，以及根据真实需求评估站内通知或实时推送。

以上为单名熟悉仓库的全栈开发者粗估，不含业务等待、历史数据清洗和第三方邮件域名认证时间。每个 Phase 独立评审、测试和发布，不建议一次性大爆炸上线。

## 18. 发布、回滚与生产影响

### 18.1 发布顺序

1. 创建功能分支与 ADR，完成模型和迁移评审；
2. 备份数据库，在预生产数据副本演练迁移；
3. 先部署新增表与兼容代码，功能开关保持关闭；
4. 启用内部管理员和少量试点用户；
5. 验证权限、写入、提醒 dry-run、通知日志和现有站点回归；
6. 配置真实邮件适配器并小流量发送；
7. 扩大组织范围，观察至少一个完整提醒周期；
8. 评审后全量开放。

### 18.2 回滚

- 应用回滚：关闭功能开关并回退到上一稳定部署；
- 调度回滚：停止触发提醒扫描，保留发件箱记录；
- 邮件回滚：禁用发送器或切到 dry-run，不删除失败/待发记录；
- 数据库回滚：首发迁移仅新增对象，应用回滚时保留新表；只有经过备份恢复演练后才允许删除；
- 数据修复：使用审计事件和导入批次定向修复，不执行无范围的批量删除。

## 19. 成本与运维评估

V1 主要复用现有 Web 与 PostgreSQL，新增成本来自数据库容量、备份、邮件发送量和少量定时任务。无需新增 Redis、常驻队列或独立服务器是当前最低运营成本方案。邮件量应按“活跃项目数 x 平均提醒次数 x 收件人数”测算，并设置每日组织上限、防止错误策略导致邮件风暴。

进入以下任一条件后再评估拆服务或引入队列：提醒积压持续超过一个扫描周期、单次扫描无法在计划窗口内完成、通知渠道超过 3 种且重试策略显著不同、独立团队需要单独发布，或客户项目模块的可用性目标与主站明显分离。

## 20. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 用户不更新数据 | 报表失真 | 下一步必填、停滞提醒、经理视图、简化移动端跟进 |
| 邮件过多导致忽略 | 提醒失效 | 合并同日提醒、频率上限、个人/项目偏好、升级分级 |
| 多人覆盖数据 | 历史丢失 | 乐观锁、版本冲突、审计事件、活动记录不可覆盖 |
| 量产/失败搬表 | 关联断裂 | 单表状态机 + 汇总视图，禁止物理搬运 |
| 权限越界 | 客户与竞争情报泄露 | 组织隔离、服务端 RBAC、导出审计、自动化越权测试 |
| 调度重复执行 | 重复邮件 | 唯一幂等键、事务领取、状态机、发送上限 |
| Web 进程内定时任务失效 | 漏提醒/重复提醒 | 外部调度器触发，数据库保存事实与心跳 |
| 历史 Excel 脏数据 | 导入污染 | 预览、字段映射、逐行错误、批次审计、可撤销导入 |
| 模块继续膨胀根目录 | 维护困难 | 独立领域目录、服务/仓储边界、ADR 与测试门禁 |

## 21. 待业务确认项与默认决策

为避免阻塞设计，以下均给出默认值；业务评审可修改配置，不影响总体架构：

| 待确认事项 | 默认决策 |
| --- | --- |
| 是否多公司/多团队 | 从第一天加入 `organization_id`，首发可只创建一个组织 |
| 量产/失败是否审批 | 主业务发起，业务经理或组织管理员确认 |
| 默认阶段 | 评估、立项、送样/验证、小批、试产、定点、量产；另有暂停、失败、归档 |
| 跟进提醒 | 前 1 个工作日、当天、逾期次日 |
| 长期未更新阈值 | 按阶段 10-30 天，可配置 |
| 邮件收件人 | 主业务必收；PM/FAE 按项目或组织策略抄送 |
| 删除保留 | 回收站 30 天；审计和通知按政策长期保留 |
| 金额/报价 | 可选且权限受控，不作为项目创建必填 |
| 附件 | 预留接口，真实需求确认后启用 |
| Excel 导入 | V1.1，上线核心台账稳定后提供 |

## 22. Codex 实施指令

Codex 在开始编码前应依次完成：

1. 阅读根目录 `AGENTS.md`、`docs/README.md`、现有认证/权限/模型/部署代码和工作树状态；
2. 用本 PRD 的 Golden Rule 结论做设计门禁，若发现与现状不一致先更新计划，不擅自改变已批准架构；
3. 建立功能分支，提交 Phase 0 的 ADR、ER 图、API 契约、页面原型和迁移/回滚计划供评审；
4. 优先构建领域模型、权限、状态机、审计和并发控制，再做页面；
5. 将提醒拆为“业务规则 -> 发件箱 -> 适配器”，禁止路由内直接发邮件；
6. 所有迁移保持向后兼容，先在 PostgreSQL 预生产副本演练；
7. 每个 Phase 完成时同步更新 `docs/architecture/`、`docs/adr/`、`docs/api/`、`docs/deployment/`、`docs/operations/` 和变更记录；
8. 未通过权限、幂等、冲突、备份恢复、回滚和现有站点回归测试，不得标记完成或发布生产。

## 23. 最终验收定义

系统可被验收为“完成”的最小结果是：团队能够在不同终端共同维护一个含多品类、多推广料号和零到多竞争方案的客户项目；系统不会静默覆盖并发编辑；能按计划和停滞规则向正确人员发送不重复且可追踪的邮件；量产、失败、归档后完整历史仍可查；项目可恢复或衍生；所有 CRUD、权限、审计、报表口径、部署和回滚均通过测试并有文档。
