# 客户项目 Phase 4 组织工作日日历部署与回滚

## 状态与安全边界

本阶段提供组织级工作日日历：管理员可将法定假日设为休息日、将周末调休设为工作日，未配置日期仍按周一至周五。提醒扫描的到期前、逾期和经理升级事件按工作日推算时应用覆盖；到期日当天与主业务停滞提醒保持自然日口径。

Golden Rule 结论：日历只影响提醒计划时间，不影响项目数据和既有发件箱记录；`shared/business_calendar` 是可复用助手，未来排班、SLA 等模块可直接使用；只加表 migration 比新建服务成本更低；统一后台表单与回滚步骤可由初学者执行；架构保持模块化单体与 PostgreSQL 事实源。

## 迁移

先备份并在同版本 PostgreSQL staging 演练；生产必须设置 `AUTO_CREATE_SCHEMA=false`：

```powershell
$env:FLASK_APP = "app:create_app"
flask db current
flask db upgrade
flask db current
```

升级前应为 `b3c4d5e6f7a8`，升级后应为 `c4d5e6f7a8b9`。本次只新增 `organization_business_day_overrides` 表（组织 + 日期唯一、范围索引、正版本号检查），不修改或回填任何既有表。

## 启用与验证

本阶段无新环境开关。部署应用后在统一后台“客户项目”页的“组织工作日日历”卡片操作：

1. 选择一个未来工作日（如周五），保存为“休息日”。
2. 预期提示“组织工作日日历已保存，未发送旧提醒已取消”；列表显示该日期覆盖结果。
3. 手工执行 `flask customer-projects scan-reminders --force`，到期前/逾期/经理升级提醒应跳过该休息日；到期日当天和主业务停滞提醒日期不变。
4. 对该日期执行“恢复默认”，版本号不匹配时预期提示他人已更新，刷新后重试成功。
5. 审计日志应包含 `organization_business_day` 的 `upserted`/`deleted` 事件，含日期、覆盖结果、策略版本和取消数量，不含敏感业务内容。

## 成功检查

- 未配置任何覆盖时，扫描结果与上线前完全一致（普通周历）。
- 覆盖新增、修改或删除后，组织提醒策略版本递增，该组织未发送的旧提醒被标记取消。
- 重复扫描不产生重复意图；已 `sent`/`dead` 的历史投递不受影响。
- 日历说明超过 120 字符或日期超出 2000–2100 年被拒绝且不产生部分写入。

## 回滚

首选回滚是部署上一稳定应用：旧应用忽略 `organization_business_day_overrides` 表并按普通周历扫描，不执行生产 downgrade。如需立即恢复普通周历而不回退应用，在统一后台删除全部日历覆盖即可，系统会自动取消未发送旧提醒并按周历重新生成。仅在备份恢复演练和单独审批后才允许清理该表。

## 常见故障

- 保存后提醒日期未变化：确认覆盖日期落在受影响项目的推算窗口内，且已重新执行扫描命令；日历不会改写已发送的记录。
- “日历覆盖已被其他管理员更新”：两人同时编辑同一日期，刷新页面后重试。
- 扫描后意图时间集中在调休工作日：确认该日期被正确保存为“调休工作日”而非“休息日”。
